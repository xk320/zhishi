# PR 自动合并轻量方案设计

## 背景

《知势》当前是 GitHub Free 私有仓库，无法使用私有仓库的原生 Auto Merge、
Branch Protection、必需评审和规则集。当前仍处于研究与架构阶段，不为此升级套餐，
也不引入外部审批服务或复杂质量门。

本设计用仓库内脚本和 GitHub Actions 建立可维护的替代流程。自动化只减少低风险
文档类 PR 在架构评审后的机械合并操作，不扩大 Codex 的评审权，也不改变高风险
变更必须人工处理的原则。

## 目标

1. Codex完成任务后继续自动创建PR。
2. 低风险PR通过资格检查后，由仓库所有者针对当前提交SHA明确批准。
3. 合并工作流在批准后重新验证资格并自动合并。
4. 任何信息缺失、提交变化、检查失败或高风险路径都默认转人工。
5. 将完整平台质量门延后到阶段2，不阻塞当前研发。

## 信任边界

### 资格检查工作流

- 由`pull_request`事件触发。
- 只授予`contents: read`和`pull-requests: read`。
- 可以检出PR内容并运行PR分支中的资格脚本，但没有仓库写权限。
- 结果用于向评审者展示问题，不能单独授权合并。

### 合并工作流

- 由`issue_comment.created`事件触发，工作流文件必须已经存在于`main`。
- 只接受登录名为`xk320`且作者关联为`OWNER`的评论。
- 精确指令格式为`/架构评审通过 <40位PR头提交SHA>`。
- 只检出`main`并运行`main`上的可信资格脚本，不执行PR分支中的脚本或工作流。
- 写权限仅用于合并PR和写入审计评论。
- REST合并请求携带预期头提交SHA，提交变化时由GitHub拒绝。

## 自动合并资格

PR必须同时满足：

1. 状态为开放且不是草稿，目标分支为`main`。
2. 来源仓库是`xk320/zhishi`，不自动处理外部仓库PR。
3. PR正文引用至少一个`任务-NNNNNN`。
4. 每个任务文件已存在于基线`main`。
5. 基线任务类型属于`文档`、`治理`或`研究规范`。
6. PR中的关联任务状态为`待评审`。
7. 变更路径全部是根目录治理Markdown或`docs/`下的Markdown。
8. PR修改的任务文件与正文引用一致。
9. 资格检查成功，PR可合并且批准SHA仍等于当前头提交。

以下情况默认拒绝自动合并：

- 修改`.github/`、脚本、源代码、配置、数据或数据库迁移。
- 交易执行、资金管理、生产环境或真实资金风险相关任务。
- 任务类型缺失、无法识别或被PR临时改成低风险类型。
- 任务文件只存在于PR而未先进入`main`。
- 外部仓库PR、草稿、冲突、失败检查或过期批准。

任务类型从基线`main`读取，PR不能通过修改自身任务类型获得自动合并资格。

## 任务状态

当前任务不让GitHub Actions直接提交到`main`更新任务状态。合并后仍由Codex按任务
中心协议提交完成证据，避免为机械状态同步建立第二套写入和循环PR系统。阶段2再评估
端到端状态同步。

## 阶段2增强

进入正式开发阶段后评估：

- GitHub Pro或组织级付费方案；
- `main`分支保护或规则集；
- 必需评审、CODEOWNERS和必需状态检查；
- 原生Auto Merge；
- 完整Quality Gate及合并后任务状态自动同步。

这些能力不作为任务-000013验收条件。

## 回滚

- 合并工作流出现异常时，可禁用或删除对应工作流；未合并PR不受影响。
- 已发生的错误合并使用普通`git revert`回滚，不改写历史。
- 资格判定脚本与策略文档随工作流一起回滚。
- 自动合并失败时不重试、不绕过，直接转人工处理。

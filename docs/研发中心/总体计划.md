# 《知势》研发总体计划

## 一、阶段结构

```text
阶段0：已完成
    ↓
阶段0.5：核心理论合同已完成
    ↓
阶段1：数据闭环证据修复
    ↓
阶段2：被阶段1证据门阻塞
    ↓
阶段3至阶段7：仅完成部分理论合同，运行能力未解锁
```

## 一点五、准入层次分离

第一阶段固定采用“独立阶段1数据证据门 + 三层准入/许可合同”边界：

1. **阶段1数据证据门**：裁决来源、时间、质量、重放、成本与执行证据及缺口；
2. **研究准入**：裁决冻结研究版本能否在限定标的和尺度内继续研究；
3. **单次交易许可**：按七道质量门裁决一个冻结决策上下文的`允许/禁止`；
4. **真实交易准入**：裁决系统是否具备使用真实资金的独立资格。

阶段1数据证据门与三层准入/许可合同之间禁止自动升级。阶段1数据门通过不等于研究已纳入；研究已纳入不等于交易许可
允许；交易许可允许不等于真实交易准入已批准。当前任务-000105仍裁决阶段1未完成、
阶段2禁止；任务-000106仍保持原成本与执行证据阻塞；真实交易准入固定为`关闭`。
模拟交易、影子决策和历史重放均不能改变真实交易准入状态。

## 三、硬门槛

在任务-000037最终审计明确放行前：

- 不训练复杂模型；
- 不报告正式胜率或收益；
- 不开展真实资金交易；
- 不使用无法证明时间对齐的数据做正式事件驱动回测；
- BTC与ETH必须分别形成证据，不得互相外推。

任务-000006只提供历史最小闭环基线；任务-000029至任务-000092的兼容证据均为历史或上游输入。自任务-000093登记并由任务-000094逐行审计后，阶段门以新正式输入和后继同版本证据为准；只有八个叶子的全部硬门通过才可放行阶段2。

## 四、任务创建原则

新任务必须：

1. 对应一个明确的决策问题或工程问题；
2. 有输入合同、输出合同和安全边界；
3. 有可观察、可复现的验收标准；
4. 标明依赖、优先级和阻塞条件；
5. 能说明它减少哪类错误交易、提高哪类净期望或增强哪项风险约束；
6. 不与《知势宣言》《知势决策标准》和《研究准入规范》冲突。

## 五、阶段评审原则

阶段不是因为任务数量完成而通过，而是因为核心能力被证据证明。任何阶段结论均允许为“不通过”“部分通过”或“需补充证据”。

## 六、阶段2研发平台增强

进入阶段2正式开发后，评估并实施：

- GitHub Pro或适合的组织级付费方案；
- `main`分支保护或规则集；
- 必需架构评审、CODEOWNERS和必需状态检查；
- 原生Auto Merge；
- 完整Quality Gate；
- 合并后任务状态的端到端自动同步。

阶段0.5使用`docs/治理/PR自动合并策略.md`定义的轻量替代流程。上述付费能力和完整
质量门不作为任务-000013验收条件，不阻塞当前研究与架构任务。

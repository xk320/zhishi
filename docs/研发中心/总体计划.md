# 《知势》研发总体计划

## 一、阶段结构

```text
阶段0：项目治理与决策合同（已完成）
    ↓
阶段0.5：理论体系建设（进行中）
    ↓
阶段1：数据资产审计与市场时间机器（等待服务器）
    ↓
阶段2：简单基准模型
    ↓
阶段3：市场状态与相关状态
    ↓
阶段4：资金轮动与标的排序
    ↓
阶段5：交易许可与风险否决
    ↓
阶段6：事件驱动回测
    ↓
阶段7：模拟交易与影子决策
```

## 二、当前推进策略

服务器恢复前，只执行不依赖真实数据的理论与治理任务：

- 任务-000007：《知势白皮书》V1.0。
- 任务-000008：《知势决策委员会》V1.0。
- 任务-000009：《知势知识图谱》V1.0。

服务器恢复后，优先恢复阶段1：

- 任务-000003：数据源发现。
- 任务-000004：数据质量审计。
- 任务-000005：历史现场重放。
- 任务-000006：最小数据闭环与最终审计结论。

## 三、硬门槛

在任务-000006完成前：

- 不训练复杂模型；
- 不报告正式胜率或收益；
- 不开展真实资金交易；
- 不使用无法证明时间对齐的数据做正式事件驱动回测；
- 不用BTC、ETH结果外推SOL。

## 四、任务创建原则

新任务必须：

1. 对应一个明确的决策问题或工程问题；
2. 有输入合同、输出合同和安全边界；
3. 有可观察、可复现的验收标准；
4. 标明依赖、优先级和阻塞条件；
5. 能说明它减少哪类错误交易、提高哪类净期望或增强哪项风险约束；
6. 不与《知势宣言》《知势决策标准》和《研究准入规范》冲突。

## 五、阶段评审原则

阶段不是因为任务数量完成而通过，而是因为核心能力被证据证明。任何阶段结论均允许为“不通过”“部分通过”或“需补充证据”。

## 六、阶段2研发平台增强

进入阶段2正式开发后，评估并实施：

- GitHub Pro或适合的组织级付费方案；
- `main`分支保护或规则集；
- 必需架构评审、CODEOWNERS和必需状态检查；
- 原生Auto Merge；
- 完整Quality Gate；
- 合并后任务状态的端到端自动同步。

阶段0.5使用`docs/治理/PR自动合并策略.md`定义的轻量替代流程。上述付费能力和完整
质量门不作为任务-000013验收条件，不阻塞当前研究与架构任务。

# 《知势》研发中心

> **宁可错过，不做低胜率交易。**

研发中心是《知势》任务、状态、证据和评审的唯一事实来源。所有工作必须先形成任务合同，再由 Codex 执行，通过 Pull Request 交付，经过架构评审后才能进入主分支。

## 一、目录结构

```text
docs/研发中心/
├── README.md              # 工作规则
├── 看板.md                # 当前任务状态
├── 总体计划.md            # 阶段与任务依赖
└── 任务/
    ├── 任务-000001.md
    └── ...
```

## 二、标准状态

任务只能处于以下状态之一：

- `待执行`：任务合同完整，可以开始。
- `执行中`：已有执行分支，Codex 正在处理。
- `阻塞`：存在明确外部依赖，暂时不能继续。
- `待评审`：已有提交和 Pull Request，等待架构评审。
- `需修复`：评审未通过，等待按意见修改。
- `已完成`：验收通过并已合并主分支。
- `已取消`：经证据证明不应继续。

禁止使用“基本完成”“差不多完成”等模糊状态。

## 三、任务执行闭环

```text
架构层创建任务
    ↓
任务进入待执行
    ↓
Codex读取最高优先级且无阻塞任务
    ↓
更新为执行中并创建独立分支
    ↓
实现、测试、自审、提交、推送
    ↓
创建Pull Request
    ↓
更新为待评审
    ↓
架构评审
    ├── 通过 → 合并 → 已完成
    └── 未通过 → 需修复 → Codex继续修改
```

## 四、Codex 自动执行规则

Codex 每次运行必须：

1. 读取根目录 `AGENTS.md`、本文件、`看板.md` 和 `总体计划.md`。
2. 只选择一个最高优先级、状态为`待执行`、依赖全部满足的任务。
3. 执行前将任务状态改为`执行中`，记录分支和开始时间。
4. 严格遵守任务中的输入合同、输出合同、安全边界和验收标准。
5. 完成后运行验证命令，记录真实结果，不得伪造通过。
6. 提交、推送并创建 Pull Request。
7. 将任务状态更新为`待评审`，写入提交 SHA、PR、交付物和已知限制。
8. 同步更新 `看板.md`。
9. 未通过验收时不得标记`待评审`或`已完成`。
10. 不得自动合并自己的 Pull Request；必须等待架构评审。

## 五、任务优先级

- `P0`：安全、数据可信度或阶段硬门槛。
- `P1`：当前阶段核心能力。
- `P2`：重要增强。
- `P3`：可延后优化。

选择顺序：优先级高者优先；同优先级按任务编号从小到大。被阻塞任务不得跳过依赖强行执行。

## 六、完成定义

任务只有同时满足以下条件才算完成：

- 所有必要交付物存在；
- 验收标准逐项通过；
- 验证命令和结果已记录；
- Pull Request 已通过评审并合并；
- 任务文件和看板已更新；
- 数据、安全、风险和已知限制已披露。

没有 Git 提交不算完成；没有 PR 不算完成；没有验收不算完成；没有证据不算完成。

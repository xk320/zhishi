## 背景

任务-000095正确建立了任务-000095→任务-000094的一次性八段固定合同修复入口。实际准备目标PR时，固定转换本身8/8逐字匹配，但`tests/研发中心/test_验证自动合并资格.py`中的合同、资源证据和CLI测试均直接把仓库当前任务-000094文件当作“修复前”输入。目标修复一旦进入`main`，这些测试会因旧片段已经不存在而永久失败。

该缺陷只在目标合同真正落地前暴露，不能通过降低测试要求或暂时接受红色`main`解决。

## 任务目标

1. 建立单一测试夹具，可从修复前或精确修复后的任务-000094正文确定性得到同一组旧版/新版合同。
2. 修复全部依赖当前仓库任务-000094为旧版的测试，保证目标合同合并前后均通过。
3. 继续逐字验证八段替换、额外字符拒绝、资源证据任务合同指纹和真实CLI正负路径。
4. 不改变生产可信规则、任务-000094合同、看板状态或数据审计结论。

## 固定执行方案

1. 在现有测试模块中新增最小辅助夹具：先尝试可信八段正向转换；若当前正文已是新版，则逐段反向重建旧版并再次正向转换证明完全一致。
2. 辅助夹具要求每个旧段或新段恰好出现一次，混合、缺失、重复或额外变体立即使测试失败。
3. 合同修复、资源证据绑定、一次性入口及真实Git CLI测试统一复用该夹具。
4. 运行目标定向测试及研发中心全量单进程测试，验证修复前基线；目标合同PR仍须再次验证修复后状态。

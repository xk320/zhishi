## 背景

任务文件已经是唯一事实来源，任务-000040和任务-000041分别建立了看板模式和外部阻塞状态
闭环。但未来仍可能出现跨载体、跨版本或跨任务合同的冲突：例如任务文件与看板分区不一致、
任务合同与PR元数据不一致、依赖形成环、现行BTC/ETH范围被历史SOL文字误读、评审证据绑定旧
提交、多个在途分支同时修改同一任务，或低权威的Issue/聊天内容试图覆盖任务合同。若没有统一
分类与安全停机规则，自动执行器可能选择“更方便”的版本，造成状态漂移、范围扩张或错误合并。

## 任务目标

建立研发中心跨载体冲突的单一裁决与安全闭环，使未来冲突能够被确定性识别、分级、记录、
可逆修复或失败关闭。任何无法由任务文件、项目硬边界和当前基线保守解决的业务语义冲突，
必须阻止执行与自动合并，不得猜测、静默覆盖或把冲突转化为成功状态。

## 固定执行方案

1. 定义冲突类别、权威优先级、证据要求、状态迁移和失败关闭语义；
2. 实现只读、确定性冲突检查器，至少覆盖任务文件/看板、任务合同/PR元数据、任务依赖、
   任务编号与重复映射、现行研究范围、状态与执行分支、评审证据基线SHA以及历史与现行
   文档边界；
3. 实现受限、可逆的修复计划或修复入口：只允许从任务文件重建派生看板和提示性元数据；
   不得由Issue、PR、聊天、旧分支或历史报告反向覆盖任务合同、研究范围或安全边界；
4. 将检查器接入任务中心验证与自动合并资格检查，任何未分类、权威来源冲突、SHA变化、
   未解决线程、资源不足或输出不确定都必须失败关闭；
5. 增加反例和回归测试，并记录机器可读的冲突代码、来源、裁决、修复动作、解除条件和
   不可变输入指纹；不保存敏感正文、原始市场数据或凭据。

## 默认工程决策

- 权威顺序固定为：资金与数据安全硬边界 → 任务文件合同 → `AGENTS.md`与任务中心规范 →
  机器看板模式 → 看板派生视图 → 总体计划与研究文档 → PR/Issue/聊天；低权威内容不得覆盖
  高权威内容；
- 任务文件之间出现同级合同冲突时，保留全部证据并返回`阻塞`，不自动选择任一版本；
- 可自动修复仅限看板等派生视图、确定性排序和本任务明确登记的提示性元数据；修复前后
  必须保留基线与头SHA，失败时不写入；
- 任务编号历史缺号、历史SOL记录和已合并证据均视为不可变事实；当前前向研究范围只接受
  BTC、ETH，历史内容不得被删除或改写为当前范围；
- 使用Python标准库、现有机器看板模式和已有验证器，不引入常驻服务、数据库、外部任务系统
  或第三方运行时依赖；验证单进程并使用受控内存参数。

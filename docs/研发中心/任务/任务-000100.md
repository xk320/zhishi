## 任务目标

1. 为BTCUSDT、ETHUSDT建立手续费、价差、深度、冲击、资金费率、行情可见性延迟和可成交量的来源身份、三类时间、版本与内容指纹链；执行延迟保持独立无法判定。

3. 按标的、Binance、USDⓈ-M、精确合约、方向、入场/退出和4/8/24/48小时主尺度分别裁决；15分钟、1小时只作事后观察窗口。
4. 使用事前冻结的查询计划和数据截止生成不可变统计快照；当前数据不得回填历史缺口，BTC与ETH不得互相补偿。
5. 本任务只登记六类可观测成本输入和行情可见性延迟；固定七项门中的执行延迟未通过前，任何叶子的成本与执行总门均不得通过，并须保存精确缺口和可自动执行的后继解除条件。

## 固定执行方案

1. 本地先冻结任务-000099最终批次、合同、执行器、只读探针、查询模板、Binance端点、字段映射、数据截止、资源上限和输出Schema；所有业务读取必须晚于冻结意图。
2. 远端入口固定为`ssh -o BatchMode=yes -o ConnectTimeout=15 -o ServerAliveInterval=5 -o ServerAliveCountMax=1 ubuntu python3 -`；记录实际UID=0和`root兼容只读`，不把root解释为专用只读账户。
3. 第一段只查询`information_schema.TABLES/COLUMNS/TABLE_PRIVILEGES/STATISTICS`获取表估算行数、Schema、权限和索引指纹，不对业务表执行精确`COUNT(*)`或无索引`MIN/MAX`；只接受`orderbook`库中能映射BTCUSDT/ETHUSDT、事件时间、到达/采集时间、买卖价或档位价格/数量的普通表。每表元数据只读一次。
4. 第二段只对第一段已冻结白名单执行预定义聚合`SELECT`；固定候选表限于`order_book_raw_snapshots`、`order_book_feature_buckets`、`order_book_market_structure_snapshots`、`order_book_public_context_snapshots`和`symbol_metadata`，实际缺表即无法判定，不改用相似表。每个冻结查询先执行一次`EXPLAIN FORMAT=JSON`并保存计划指纹；仅允许`system/const/ref/range`或`Select tables optimized away`，必须命中冻结的标的+时间索引，单查询估算扫描不超过25万行、全批次不超过100万行。任一`ALL/index`全表/全索引扫描、未命中索引、估算超限、计划漂移或负载告警即停止对应来源。
5. 每张表最多一次获取覆盖边界聚合、每个已批准指标最多一次业务聚合，全批次SQL总数不超过24条（不含对应`EXPLAIN`）；每条业务查询只允许执行一次，超时不重试。禁止`SELECT *`、无界返回、锁表、临时表、存储过程、DDL、DML、`INTO OUTFILE`和数据库备份。
6. Binance网络只允许官方HTTPS主机和公开USDⓈ-M端点，候选固定为`exchangeInfo`、`depth`、`premiumIndex`与`fundingRate`；每次响应绑定URL模板、参数、服务器时间、采集时间、响应SHA和Schema指纹。需要签名、API Key、账户或专属费率的端点禁止调用。
7. 手续费只接受可验证的公开非账户费率版本；无法证明版本时保持无法判定。价差、深度、冲击和可成交量由同一订单簿快照按固定名义规模确定性计算。事件/到达/采集时间差只能登记为行情可见性或采集延迟，不得标记执行延迟通过。执行延迟必须由同一历史现场的版本化模拟执行生命周期（委托发送、确认/成交、排队或撤单时间）证明；本任务不实施该模拟，因此执行延迟和成本与执行总门保持无法判定。
8. 发布前重算全部输入、查询模板、Schema、索引、执行计划、统计分母和输出指纹；临时目录回读、资源门和内核原子no-replace均通过后才追加发布。

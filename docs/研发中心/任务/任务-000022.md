## 目标

修复历史重放验证中的确定性与快照合同缺口，使系统能够证明指定历史时间点可基于冻结输入集合进行一致性重放。

## 固定执行方案

采用方案A“内容寻址的不可变重放快照合同”，合同版本固定为
`replay-snapshot-contract-1.0`。仅使用Python标准库，不新增依赖、服务、数据库或通用
远端命令入口。

### 第一门：冻结快照身份

1. 同时绑定带时区的历史时间与决策时间。
2. 数据版本必须是确切不可变版本；空值、`latest`和`current`一律拒绝。
   快照逻辑标识与数据版本只允许由中英文字符、数字及`._:/-`构成的1至128位稳定
   标识。禁止前后空白；禁止以`._:/-`为边界出现`latest`或`current`浮动令牌；
   禁止任何带命名空间或前缀的纯ISO日期/日期时间令牌及10/13位Unix时间戳令牌猜身份。
3. 对按已冻结业务键稳定排序的完整输入记录规范JSON计算SHA-256，与声明哈希
   不一致时失败安全。规范JSON禁止NaN和正负Infinity，避免跨实现非标准序列化漂移。
4. 冻结非空输入资产集合、业务键，以及事件、到达、采集时间字段和每个字段的
   `已冻结`状态；不得根据字段名猜测语义。
5. 正式覆盖是一行一个`asset_id`的逐资产验证单元，因此冻结输入资产集合必须严格等于
   只含当前资产编号的集合。额外未知资产或已知但未通过第一门的资产均以
   `input_asset_set_missing`失败安全，不得进入第二门。资产集合指纹同时绑定排序后的
   资产身份、输入数据版本和数据哈希。
6. 快照使用稳定逻辑标识和内容指纹版本标识。版本标识、快照记录编号和资产集合
   指纹只能由验证器生成，不接受调用方注入。输入对象冻结后的变化不得改变快照。

### 第二门：冻结快照重放

1. 仅从通过第一门的不可变快照取数。
2. 使用`到达时间 <= 决策时间`闭区间构造历史可见集合；未来到达记录必须拒绝。
3. 基于同一冻结快照连续重放两次，比较可见记录数和输出指纹。
4. 对可见数量、未来拒绝状态与输出指纹生成独立重放结果SHA-256。
5. 两次输出不一致时以`output_hash_mismatch`拒绝，不得重试或猜测为通过。
6. 重放前必须使用与冻结阶段相同的单一规范函数深解冻并重新计算全部身份。逐项核对合同
   版本、逻辑标识、双时点、数据版本/哈希、资产集合/指纹、业务键、三时间字段/冻结状态、
   快照版本标识和记录编号；任一漂移均不得返回通过或沿用旧版本标识。

## 输出合同

输出：

- 重放结果hash；
- 一致性验证结果；
- 不可重放原因分类；
- 修复建议。

正式CSV保留任务-000005的22个固定列及其顺序，并在末尾追加：

```text
快照记录编号,快照合同版本,快照逻辑标识,快照版本标识,输入数据版本,
输入数据哈希,输入资产集合指纹,重放结果哈希,不可重放原因代码,修复建议
```

无证据字段写带原因码的`无法判定`，不得留空、填零或生成虚假编号。原因码与中文修复建议
统一映射，至少覆盖：`input_identity_drift`、`input_scan_incomplete`、
`decision_record_missing`、`snapshot_contract_incomplete`、`data_version_missing`、
`data_hash_missing`、`data_hash_mismatch`、`input_asset_set_missing`、
`available_fields_unproven`和`output_hash_mismatch`。

`input_scan_incomplete`是第一门硬前置，不得被下游表面完整的快照证据覆盖。
`data_hash_mismatch`同时用于表示重放前重算时发现的全快照身份或内容指纹漂移；
修复时必须创建新快照，不得改写或沿用旧版本标识。

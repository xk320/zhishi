# 《知势》任务中心规范 V1.1

> 任务文件是任务合同与任务状态的唯一事实来源。

## 一、目的

本规范统一《知势》的任务登记、选择、执行、交付和状态维护，消除任务文件与 GitHub Issue 并列为事实来源造成的范围和状态漂移。

本规范只建立轻量仓库内治理，不引入外部任务系统、常驻机器人或数据库。

## 二、唯一事实来源

每项任务必须且只能由以下路径中的一个文件定义：

```text
docs/研发中心/任务/任务-NNNNNN.md
```

任务名称、目标、类型、优先级、状态、依赖、输入合同、输出合同、工作范围、安全
边界、验收标准和交付记录均以该任务文件为准。

没有任务文件的事项不构成可执行任务。即使存在聊天指令、GitHub Issue、Pull Request、评论、标签或分支，也禁止据此直接实现；应先创建任务文件并通过治理变更进入主分支。

任务-000012 是建立本规则的一次性引导迁移。自本任务合并后，不再允许同类例外。

## 三、其他载体的职责

| 载体 | 职责 | 不得承担的职责 |
| --- | --- | --- |
| `docs/研发中心/任务/` | 定义任务合同、执行资格、状态和交付证据 | 无 |
| `docs/研发中心/看板.md` | 汇总任务文件的当前状态，便于浏览 | 不得独立创建任务或覆盖任务文件状态 |
| `docs/研发中心/总体计划.md` | 表达阶段、方向、依赖和硬门槛 | 不得充当逐任务实时状态表 |
| GitHub Issue | 可选的讨论、提问、证据附件和外部关联 | 不得定义任务合同、状态、优先级或执行资格 |
| Pull Request | 承载任务交付、评审和合并证据 | 不得替代任务文件或自行扩大任务范围 |
| 聊天与评论 | 提供指令、反馈和澄清 | 不得在缺少任务文件时成为自动执行依据 |

发生冲突时，任务文件优先。发现冲突的执行器必须停止冲突部分，修正看板或提出治理修复，不得从 Issue、PR 描述或聊天中挑选更方便的版本。

## 四、编号与创建规则

1. 文件名使用六位流水号：`任务-NNNNNN.md`。
2. 文件一级标题使用`任务-NNNNNN：任务名称`。
3. 新编号不得复用、跳转到已有编号或依赖 Issue 编号。
4. GitHub Issue 编号与任务编号没有映射关系；关联时必须写明“讨论关联”。
5. 新任务必须先以任务文件进入 `main`，状态为`待执行`、`需修复`或`阻塞`，之后才可被自动执行器选择。
6. 修复意见若需要独立任务，必须先创建修复任务文件；评审评论或 Issue 本身不能使任务获得执行资格。

## 五、任务文件最低合同

每个可执行任务文件至少包含：

- 状态；
- 类型；
- 优先级；
- 阶段；
- 依赖与阻塞条件；
- 背景；
- 任务目标；
- 输入合同；
- 输出合同；
- 工作范围；
- 不在范围；
- 安全边界；
- 验收标准；
- 验证命令或可复现验证方式；
- 完成定义。

状态为`待执行`或`需修复`的任务还必须明确：

- 唯一执行方案；
- 方案状态；
- 执行授权；
- 默认工程决策规则；
- 允许停止并请求人工决策的条件。

开始执行后还必须记录执行分支和开始时间。进入`待评审`前还必须记录提交 SHA、Pull Request、交付物、验证命令与结果、已知限制、数据与安全影响以及需要人工决策的问题。

历史任务合同可以在治理变更中逐步补齐，但状态和看板必须立即保持一致。

任务类型用于描述交付风险和自动合并资格。新任务必须使用明确、稳定的中文类型。
允许自动交付的精确类型为`文档`、`治理`、`研究规范`、`数据治理`、`数据审计`、
`数据工程`、`基础设施验证`、`策略研究`、`研究工程`、`模拟交易`、`测试`和`工具`。
缺少类型、类型未知或属于其他类型的任务不能自动合并。PR不得通过修改自身任务类型获得
资格，自动合并判定必须读取基线`main`中的任务类型。

当前系统只进行策略研究和基于实时数据的模拟交易，不连接真实资金。生产写入、凭据、
原始数据破坏和不可逆操作始终需要任务合同以外的明确授权，不能由任务类型或自动合并
白名单隐式取得。

## 六、默认直接执行与方案合同

`待执行`表示任务合同和依赖均完整，并且执行方案已经批准。执行器选择任务后应作为
自动化工具直接推进，不得把普通工程取舍重新包装成A/B/C选项交给用户。

### 方案字段

新建或补齐任务时使用以下字段：

```text
- 执行方案：方案A“唯一方案名称”
- 方案状态：已批准执行
- 执行授权：Codex直接执行，不得再次要求用户选择方案
```

任务文件只保留一个获批方案。备选方案可以在设计依据中简短记录淘汰原因，但不得在
认领时重新发起选择。`方案状态`不是`已批准执行`的任务不得标记为`待执行`，应标记为
`阻塞`并写明缺少的外部决策。

### 默认工程决策

合同范围内存在多种实现方式时，执行器依次选择：

1. 资金、数据和凭据风险最低；
2. 证据最完整、失败语义最保守；
3. 依赖最少、模块最小、最容易复现和回滚；
4. 复用仓库既有模式和标准库；
5. 在仍然等价时选择实现与验证成本最低的方案。

执行器可以在设计或PR中记录选择依据，但不得因此暂停等待用户确认。

### 允许请求人工决策的条件

只有以下条件之一成立时可以停止：

- 需要新增真实账号、凭据、生产权限或外部付费能力；
- 需要修改生产服务、数据库、权限、防火墙、原始数据或执行不可逆操作；
- 两项同等优先级的任务合同要求直接冲突，且保守停止不能解决；
- 缺少会改变业务目标、风险门槛或正式输出含义的外部事实；
- 继续执行必然超出任务文件的范围或安全边界。

数据证据不足、结果为`无法判定`、普通库选择、文件组织、测试结构、命名或可逆实现
细节不属于人工决策条件。此时应采用保守默认值继续交付证据，不得提出A/B/C选项。

本规则不授权绕过独立子智能体评审、真实资金、生产安全、数据合同或不可逆操作确认。

## 七、标准状态与流转

任务状态只允许：

- `待执行`：合同完整、依赖满足，可以开始；
- `执行中`：已经认领并在独立分支执行；
- `阻塞`：存在明确依赖或外部条件，当前不能推进；
- `待评审`：交付与验证记录完整，Pull Request 等待评审；
- `需修复`：评审发现明确问题，等待按任务合同修复；
- `已完成`：验收通过且 Pull Request 已合并；
- `已取消`：有证据证明任务不再执行。

禁止使用“已完成任务拆分”“基本完成”“处理中”等自定义状态。补充语义应写入结果、阻塞原因或执行记录，不得写入状态字段。

允许的主要流转为：

```text
待执行 → 执行中 → 待评审 → 已完成
                    ↓
                  需修复 → 执行中 → 待评审

待执行 / 执行中 / 需修复 → 阻塞
阻塞 → 待执行 / 需修复
任一未完成状态 → 已取消
```

未经评审并合并，不得从`待评审`直接写为`已完成`。

## 八、看板一致性

看板是任务文件的派生视图，必须满足：

1. 每个任务文件在看板中恰好出现一次。
2. 看板分区与任务文件的`状态`完全一致。
3. 任务编号、名称、优先级、分支、PR 和阻塞原因不得与任务文件冲突。
4. 同一次状态变更必须同时修改任务文件和看板。
5. 如果不一致，任务文件为准，并在当前治理变更中修复看板。

### 看板模式合同

看板各状态分区的表头、分隔行和列顺序只定义在
`docs/研发中心/任务看板模式.md`。该文件以UTF-8 JSON保存，包含版本和内容指纹，由可信资格检查器、
状态闭环校验和研发中心测试共同加载；文档和看板不得另行定义同等权威的模式。

当前规范中“待评审”分区的列名固定为`PR`。`Pull Request`或其他别名不是有效模式；
发现缺列、重复表头、未知别名、错分区或模式指纹不一致时必须失败关闭，并在当前治理PR
中修复，不得为兼容方便静默放行。

`总体计划.md` 只维护阶段和方向，不要求逐项复制任务状态；不得根据总体计划中的文字覆盖任务文件。

## 九、认领与防重复执行

执行器选择任务前必须：

1. 拉取最新 `main` 并扫描全部任务文件；
2. 拒绝没有任务文件的 Issue 或评论请求；
3. 按状态、依赖、优先级和编号选择任务；
4. 检查该任务是否已有远程执行分支或未关闭 Pull Request；
5. 若存在，读取该分支中的同一任务文件确认最新在途状态，不得仅凭 PR 标题或 Issue 标签判断；
6. 没有重复执行后，创建或继续任务文件规定的独立分支；
7. 将任务文件和看板同步更新为`执行中`。

远程分支和 Pull Request 只用于定位在途任务文件及避免重复执行，不拥有修改任务合同或状态的权限。

## 十、GitHub Issue 规则

GitHub Issue 可以记录讨论、问题背景、评审意见和附件。若需要关联任务，使用以下表述：

```text
讨论关联：GitHub Issue #NN（非任务事实来源）
```

禁止：

- 因 Issue 有`repair`、`bug`或优先级标签就直接执行；
- 用 Issue 正文覆盖任务文件的范围或验收标准；
- 用关闭 Issue 代替任务验收或完成状态；
- 把没有任务文件的 Issue 加入自动任务队列。

## 十一、Pull Request 规则

每个 Pull Request 必须在标题或正文明确引用至少一个任务编号，并包含：

- 关联任务编号；
- 修改内容与交付物；
- 验收结果；
- 实际执行的验证命令与结果；
- 已知限制；
- 数据与安全影响；
- 回滚方式。

普通任务交付PR只关联一个任务；合并后状态闭环PR才可按唯一后继规则最多关联两个任务。需要
多个独立交付时必须拆分PR。PR不得新增任务文件中没有授权的范围。

### 自动评审与合并规则

Codex完成任务后必须自动创建Pull Request，并由主执行器组织两个独立只读子智能体评审。
不再要求仓库所有者逐PR人工批准。只有同时满足以下条件才能自动合并：

1. PR正文以严格`## 关联任务`区段引用任务，并以`## 变更类型`声明`任务交付`或
   `合并后状态闭环`；新任务使用独立的`任务登记`变更类型；
2. `任务登记`必须且只能新增一个完整任务合同，状态为`待执行`或`阻塞`，编号为基线
   最大编号加一且不得复用历史缺号；只允许同步看板和对应设计文档；
3. 任务文件存在于基线`main`，任务交付的基线状态为`待执行`或`需修复`，基线类型属于
   文档、治理、研究规范、数据治理、数据审计、数据工程、基础设施验证、策略研究、
   研究工程、模拟交易、测试或工具；已完成任务不得重放控制面授权；
4. 两个不同评审者分别承担治理/架构和范围/安全角色，均`APPROVE`且P0=P1=0；
5. 主执行器已运行任务要求的真实验证，结构化证据绑定当前基线和头提交SHA；
6. 修复最多三轮；每次新增提交后全部旧评审和旧证据失效；
7. `main`可信规则复验同仓库来源、`main`目标、非草稿、路径资格、未解决线程、
   `CHANGES_REQUESTED`、当前头检查和GitHub可合并状态；
8. 合并API携带当前40位精确头SHA，状态或SHA变化时失败关闭。

文档类任务交付只允许根目录指定Markdown和`docs/**/*.md`。受控数据与研发任务还可以在
精确扩展名白名单下修改`config/`、`src/`、`scripts/`、`tests/`和`artifacts/`；所有路径
必须是新增或修改的`100644 blob`，拒绝删除、重命名、符号链接、子模块和可执行文件，
并限制为最多500个文件、单文件5 MiB、合计25 MiB。文本必须严格UTF-8解码并通过凭据
扫描。基线任务明确写有`自动合并范围：治理自动化`时，才额外允许两个自动合并工作流和
`scripts/研发中心/*.py`；`tests/研发中心/*.py`仍属于测试路径，但不得据此修改可信脚本。

合并后状态闭环必须使用独立PR，只允许一个任务`待评审→已完成`，可同时把唯一后继从
`阻塞→待执行`，且只能修改关联任务文件和看板。除状态、合并事实和唯一后继的
阻塞解除字段外，任务合同必须与基线逐行一致；合并事实必须可由`main`中真实提交复算。
完整证据、权限和失败处理见
`docs/治理/PR自动合并策略.md`。

GitHub Pro、Branch Protection、必需平台评审、CODEOWNERS、原生Auto Merge和完整
Quality Gate延后到阶段2，不阻塞当前轻量闭环。

## 十二、漂移检查

提交前至少执行以下检查：

1. 枚举全部`任务-NNNNNN.md`，确认编号唯一。
2. 确认每个任务状态属于七种标准状态。
3. 确认每个任务在看板中只出现一次且分区一致。
4. 搜索把 GitHub Issue 描述为任务合同或执行入口的冲突表述。
5. 对修改的 Markdown 文件运行格式检查。
6. 运行`git diff --check`。

任何检查失败都不得进入`待评审`。

# 《任务与验收规范》V1

> 任务登记、状态和任务中心载体边界以`docs/研发中心/任务规范.md`为准；本文件补充任务合同内容与验收写法。

## 一、目的

《知势》采用 Codex 和自动化代理持续开发，不以传统工期、甘特图或固定迭代周期作为主要管理方式。

项目通过以下闭环推进：

```text
目标
  ↓
任务合同
  ↓
独立分支实现
  ↓
自动验证与自审
  ↓
Pull Request
  ↓
验收
  ↓
合并或继续迭代
```

任务是否完成，只由验收标准决定，不由“代码已经写完”或“投入时间足够”决定。

## 二、任务类型

| 类型 | 说明 | 常用提交前缀 |
| --- | --- | --- |
| 研究任务 | 验证可证伪假设，结论可以是淘汰 | `research:` |
| 数据任务 | 采集、审计、清洗、对齐、存储和重放 | `feat:` / `fix:` |
| 工程任务 | 实现明确接口与系统能力 | `feat:` |
| 风控任务 | 增加风险质量门、监控或降级能力 | `feat:` / `fix:` |
| 文档任务 | 建立术语、合同、规范与说明 | `docs:` |
| 修复任务 | 修复已证实的行为偏差 | `fix:` |
| 实验任务 | 不进入主决策链的探索性工作 | `research:` |

## 三、统一任务合同

每个 `docs/研发中心/任务/任务-NNNNNN.md` 任务文件必须包含以下内容。GitHub Issue只能作为可选讨论关联，不能代替任务合同。

### 1. 背景

说明当前问题、已有能力和为什么需要执行。

### 2. 任务目标

用一句话说明任务完成后新增的可验证能力。

### 3. 决策问题或工程问题

- 研究任务：明确帮助系统回答什么交易问题。
- 工程任务：明确解决什么接口、可靠性或运行问题。

### 4. 输入合同

至少定义：

- 数据来源。
- 文件、表、接口或事件。
- 时间范围与粒度。
- 时区与单位。
- 数据质量前提。
- 依赖版本。

### 5. 输出合同

至少定义：

- 交付物路径。
- 输出字段。
- 格式与单位。
- 错误与降级行为。
- 版本与追溯信息。

### 6. 工作范围

明确本任务必须完成的内容。

### 7. 不在范围

明确禁止顺手扩展的内容，防止任务无限膨胀。

### 8. 安全边界

至少检查：

- 是否可能删除或覆盖原始数据。
- 是否会修改生产数据库。
- 是否涉及密钥和真实账户。
- 是否可能产生真实交易。
- 是否可能使用未来信息。
- 是否可能引入无法回滚的操作。

### 9. 验收标准

必须是可观察、可复现、尽可能可机器验证的标准。

### 10. 验证命令

给出能够重复执行的测试、审计、静态检查或生成命令。

### 11. 完成定义

只有全部必要验收项通过，任务才可以关闭。

## 五、验收标准写法

### 合格示例

- 对 BTC、ETH 分别随机选择至少三个历史时刻，能够只使用当时已到达的数据重建市场状态。
- 同一输入和版本重复运行三次，输出完全一致。
- 手续费、滑点、资金费率和执行延迟均进入净收益计算。
- 所有单元测试、类型检查和数据审计命令退出码为 0。
- 数据异常时输出“禁止交易”，而不是继续使用缺失值。

### 不合格示例

- 代码看起来合理。
- 模型效果不错。
- 胜率比较高。
- 性能足够快。
- 基本没有问题。

无法测量的标准不构成验收标准。

## 六、研究任务附加要求

研究任务必须遵守 `docs/研究/研究准入规范.md`，并补充：

- 明确基准。
- 样本内与样本外切分。
- 滚动或前推验证。
- 成本与延迟假设。
- 失败样本。
- 稳健性与敏感性。
- 结论允许为“淘汰”。

研究任务禁止以“新增一个指标”为完成标准。必须证明该指标解决了具体决策问题。

## 七、分支规范

建议分支格式：

```text
agent/<任务编号>-<简短说明>
research/<研究编号>-<简短说明>
fix/<问题编号>-<简短说明>
```

示例：

```text
agent/000001-data-audit
research/2026-0001-relative-strength-persistence
fix/000014-arrival-time-alignment
```

禁止直接在主分支进行尚未验收的复杂开发。

## 八、提交规范

提交应保持单一目的，常用格式：

```text
docs: 建立决策卡模板
feat: 实现统一事件时间轴
research: 完成相对强度持续性基准
fix: 修复到达时间对齐错误
test: 增加未来数据泄漏测试
```

提交信息不得使用无意义的 `update`、`changes`、`wip` 作为最终交付提交。

## 九、Pull Request 验收清单

每个 PR 必须说明：

- 关联任务编号。
- 可选的 GitHub Issue 讨论关联。
- 变更目标。
- 主要交付物。
- 验收标准逐项结果。
- 验证命令及结果。
- 数据兼容性。
- 安全影响。
- 性能影响。
- 已知限制。
- 回滚方式。

合并前必须检查：

- [ ] 没有未来数据泄漏。
- [ ] 没有提交密钥或敏感信息。
- [ ] 没有破坏性修改原始数据。
- [ ] 术语符合《知势词典》。
- [ ] 新研究符合准入规范。
- [ ] 异常状态能够安全降级。
- [ ] 测试和审计结果可复现。
- [ ] 文档与实现一致。

## 十、阻塞与并行原则

可以并行：

- 项目治理与数据审计。
- 文档合同与测试骨架。
- 不依赖真实数据结果的接口设计。

不得越过依赖：

- 数据闭环未通过，不得宣称基准模型结果可信。
- 基准模型未建立，不得证明复杂模型有效。
- 事件驱动回测未通过，不得进入模拟交易验收。
- 模拟与影子决策未通过，不得启用真实资金。

任务因依赖被阻塞时，应完成可以独立验证的部分，并在报告中明确阻塞项，不得用猜测填补缺口。

## 十一、Codex 持续执行要求

当用户授权自动执行后，Codex 可以在以下范围持续迭代，无需逐步确认：

- 与已批准系统蓝图一致。
- 不涉及真实资金。
- 不删除或迁移原始数据。
- 不改变生产服务。
- 不新增高风险外部权限。
- 不降低既有质量门。

遇到以下情况必须停止并请求确认：

- 真实交易或账户权限。
- 删除、覆盖或不可逆迁移数据。
- 修改生产数据库或生产服务。
- 新增显著成本。
- 需要密钥、私密账户或外部授权。
- 需要放宽风险限制或研究准入标准。

## 十二、任务关闭报告

```text
任务：
状态：完成 / 部分完成 / 阻塞
分支：
Pull Request：
合并提交：
交付物：
验收结果：
验证命令：
关键指标：
已知限制：
数据与安全影响：
未完成项：
下一任务建议：
```

任务关闭后，下一任务必须由已验证结果驱动，而不是由功能列表驱动。

# 《知势》PR自动评审与合并策略 V2.0

> 自动化负责组织独立评审、修复、复验和精确提交合并；任何失败都必须关闭合并路径，
> 不能降低任务、研究、数据、交易或风险门槛。

## 一、适用阶段与平台边界

本策略适用于当前GitHub Free私有仓库，使用Codex本地执行器和两个GitHub Actions工作流：

- Codex执行器：实现、创建PR、组织子智能体评审、自动修复、串行验证和提交评审证据；
- `pr-auto-merge-eligibility.yml`：从PR基线提交检出可信脚本，只读判断任务和路径资格；
- `pr-auto-merge.yml`：由仓库所有者身份下的Codex执行器触发，复验结构化评审证据并
  合并精确SHA。

不要求仓库所有者逐PR人工批准。GitHub Pro、Branch Protection、CODEOWNERS、原生
Auto Merge和完整Quality Gate延后到阶段2。

## 二、信任边界与职责

| 角色 | 职责 | 禁止事项 |
| --- | --- | --- |
| 主执行器 | 实现、修复、验证、生成证据和触发可信合并 | 不得伪造评审或绕过失败门 |
| 治理与架构评审者 | 只读核对任务、依赖、状态、架构和范围 | 不编辑文件、不运行全量测试、不使用凭据 |
| 范围与安全评审者 | 只读核对安全、数据、资源和回滚 | 不编辑文件、不访问服务器、不使用凭据 |
| 资格工作流 | 从基线运行可信资格脚本 | 不检出或执行PR头脚本，无写权限 |
| 合并工作流 | 复验资格、评审证据、线程、检查和实时SHA | 不执行PR头代码，不扩大任务范围 |

只有`main`上的规则、脚本和工作流属于可信控制面。PR正文、任务文件改动、`AGENTS.md`
改动、评论、标签和PR头提交全部是不可信输入，只能被解析或比较，不得直接执行。

## 三、标准闭环

```text
任务文件已在main并满足执行条件
    ↓
主执行器实现、串行验证、创建PR并更新待评审状态
    ↓
两个独立只读子智能体绑定当前base/head SHA评审
    ├── P0/P1存在：主执行器修复并提交，新SHA使旧评审全部失效
    │               最多重复三轮
    └── 两者APPROVE且P0=P1=0
    ↓
主执行器对最终SHA串行运行一次完整验证并生成结构化证据
    ↓
main可信工作流复验资格、证据、线程、检查和实时GitHub状态
    ├── 通过：以预期头SHA合并
    └── 失败：关闭合并路径，保留PR等待自动修复或资源恢复
    ↓
从最新main创建独立“合并后状态闭环”PR，完成任务并解除唯一后继
    ↓
该状态PR执行同样的双评审、精确SHA和自动合并流程
```

不允许管理员绕过、强制推送、修改检查结论或把不符合资格表现为成功。

## 四、PR合同

PR正文必须包含严格二级标题：

```markdown
## 关联任务

- 任务-000038

## 变更类型

- 任务交付
```

`关联任务`只接受逐行任务编号，可带括号说明。正文其他位置出现的任务编号不参与资格
判定。`变更类型`只能是：

- `任务登记`；
- `任务交付`；
- `合并后状态闭环`；
- `阻塞任务合同修复`；
- `任务合同冲突修复`。

这避免已知限制、后续计划或讨论引用被错误扩展为任务合同。

## 五、任务与路径资格

### 任务登记

任务文件仍是唯一事实来源。登记PR必须且只能引用一个新任务，基线`main`中不存在该任务，
头提交状态只能为`待执行`或`阻塞`。任务编号必须为基线最大编号加一，历史缺号000026
不得复用；状态、类型、阶段、优先级、执行方案、方案状态、执行授权和并行规则必须唯一，
14个最低合同章节必须齐全，方案状态必须为`已批准执行`。

登记只允许新增任务文件、修改看板和新增对应设计文档。任务行的状态、名称、优先级、
前序依赖与阻塞原因必须可由合同精确复算；不得夹带脚本、配置、产物、测试或既有任务
修改。`main`可信检查器从基线Git树有界加载全部任务编号，从PR头读取普通文件事实，
不执行PR头代码。

### 任务交付

必须同时满足：

1. 每个关联任务已存在于基线`main`；
2. 基线任务类型属于文档、治理、研究规范、数据治理、数据审计、数据工程、基础设施验证、
   策略研究、研究工程、模拟交易、测试或工具；
3. PR头任务状态为`待评审`；
4. 实际修改的任务文件与正文关联任务完全一致；
5. 变更路径、扩展名、Git对象、数量、体积和敏感信息均通过对应白名单。

文档、治理和研究规范交付只允许`AGENTS.md`、`README.md`、`《知势宣言》.md`或
`docs/**/*.md`。受控研发类型还允许：

- `config/`：`.json`、`.yaml`、`.yml`、`.toml`；
- `src/`：`.py`、`.js`、`.jsx`、`.ts`、`.tsx`、`.json`；
- `scripts/`：`.py`、`.sh`，路径任何层级不得出现交易、部署、生产、真实账户、数据库、凭据、
  密钥、deploy、production、trading、order、secret、credential等保留路径段或文件名；
- `tests/`：`.py`、`.js`、`.jsx`、`.ts`、`.tsx`、`.json`；
- `artifacts/`：`.json`、`.csv`、`.md`，仅允许新增小型、脱敏、不可变证据，不允许修改既有产物。

上述文件必须为新增或修改的`100644 blob`，拒绝删除、重命名、符号链接、子模块和可执行
文件；最多500个文件，单文件不超过5 MiB，合计不超过25 MiB。文本必须严格UTF-8解码并拒绝
NUL/控制字符、私钥、令牌、明文密码、真实账户标识、未经合同允许的网络目标和常见云凭据。
资格原因只能报告路径和门禁，不回显敏感正文。

只有基线任务明确包含：

```text
- 自动合并范围：治理自动化
```

才额外允许：

- `.github/workflows/pr-auto-merge.yml`；
- `.github/workflows/pr-auto-merge-eligibility.yml`；
- `scripts/研发中心/*.py`。

其中 `scripts/研发中心/*.py` 与两个自动合并工作流属于可信控制面，普通受控研发任务即使
允许修改测试（包括 `tests/研发中心/*.py`），也不能修改这些路径。该授权不能扩大到其他
工作流、真实资金、生产写入、凭据、原始数据破坏或不可逆操作。
《知势》当前只进行策略研究和基于实时数据的模拟交易；白名单只控制仓库交付资格，不授予
服务器、数据库、账户或生产环境权限。最终合并仍必须绑定精确头SHA。

任务-000095建立一个不可复用的阶段1审计例外：只有关联任务精确为任务-000094、变更类型为
`任务交付`时，允许普通`100644` UTF-8源码
`scripts/审计/阶段1时间质量扫描器.c`；其他任务、路径、原生扩展名、对象、动态库、可执行位、
删除、重命名和符号链接继续失败关闭。任务-000094还必须新增唯一最终批次摘要，记录固定
Python主控、固定编译、固定解压和固定扫描各角色、成员并行度1，以及协议
`zhishi-process-group-rusage/v1`下每个角色的非零峰值RSS。测量平台固定为
`darwin-rusage-maxrss-by-process/v1`、单位固定为字节；编译、解压与扫描峰值之和作为子进程
保守上界，再与主控峰值相加。批次身份、执行器、配置、任务合同和C源码指纹必须与PR最终头文件
逐项绑定；缺失角色、零值、平台伪装、指纹漂移、保守和不守恒或超过512MiB时不得自动合并。

### 合并后状态闭环

只允许修改关联任务文件和`docs/研发中心/看板.md`，并且：

- 每个状态闭环PR只能选择一种模式：一个任务从`待评审`改为`已完成`、一个任务从
  `待执行/执行中/需修复`进入`阻塞`，或一个任务从`阻塞`恢复为`待执行/需修复`；
- 完成模式可以把唯一后继从`阻塞`改为`待执行`，阻塞进入和阻塞恢复模式不得夹带完成、
  解锁或其他任务迁移；
- 进入阻塞只允许更改状态、当前阻塞原因和解除条件。若基线状态为`待执行`且此前没有执行
  元数据，可以一次性追加固定位置的执行分支、开始时间和`## 执行记录`；记录必须且只能包含
  `执行分支`、`开始时间`、`尝试命令`、`结果`、`外部证据`、`阻塞原因`、`解除条件`、
  `数据与安全`八个字段，外部目标只允许逻辑别名`ubuntu`，不得含IP、域名、主机地址、原始日志或凭据。
- 阻塞恢复只允许更改状态、当前阻塞原因和解除条件，既有执行元数据与记录必须逐字保持；
- 完成任务只允许更改状态并新增合并时间和合并提交SHA；唯一后继只允许更改状态、当前
  阻塞原因和解除条件，其余任务合同必须逐行不变；
- 看板必须按机器模式移动对应任务行，并能由任务文件状态、优先级、名称、依赖、阻塞原因、
  分支和PR精确复算；
- 后继的`唯一前序依赖`必须指向本次完成任务，不得解锁无关任务；
- 合并提交SHA、时间和PR必须与main中真实合并提交的祖先关系、提交时间和
  merge commit主题一致；禁止其他状态迁移和内容交付。

## 七、合并实时硬门

合并工作流必须再次确认：

1. 触发身份为仓库所有者`xk320`，来源仓库为`xk320/zhishi`；
2. 目标分支为`main`，PR开放、非草稿且GitHub确认`mergeable_state=clean`；
3. base和head SHA与评审证据完全一致，复验期间没有变化；
4. `main`可信资格脚本重新运行通过；
5. 当前head的资格检查已完成且为`success`；
6. 没有未解决评审线程或`CHANGES_REQUESTED`；
7. 两个独立评审和主执行器验证证据通过；
8. 合并API携带预期40位head SHA。

合并步骤内在调用API前立即重取PR、聚合评审决定、全部评审线程和当前检查。在无
Branch Protection的当前阶段，GitHub不提供“评审状态与合并”的单一原子API；精确head
SHA可防止代码竞态，最后一刻重取用于将评审状态竞态窗口压缩到最小。完整平台原子门延后到
阶段2的Branch Protection实施。

任一项失败立即停止，不自动猜测、不把`neutral`或“评估已运行”当作通过。

## 八、资源控制

- 最多同时两个只读评审者，不允许评审者继续派生子智能体；
- 测试始终单进程，Node使用`--max-old-space-size=256`；
- 内存压力警告时降为一个评审者且不并行测试；
- 内存压力危急或可用内存低于20%时暂停新评审和测试；
- 可用磁盘低于5 GiB时禁止新工作树和大产物；
- 不终止或改变用户已有进程；命令设置超时和输出上限。

## 九、失败、状态闭环与回滚

评审问题由主执行器自动修复；第三轮后仍有P0/P1时将任务标记`阻塞`，记录问题和解除
条件。PR冲突、检查失败、SHA变化、GitHub API拒绝或资源不足时保留PR，等待自动修复或
资源恢复，不要求人工审批，也不得绕过。

GitHub Actions不直接提交`main`。合并后由Codex从最新`main`创建独立状态闭环PR，避免
工作流持有通用仓库写入逻辑或形成第二任务事实源。

回滚方式：

- 工作流或脚本异常：通过独立PR普通`revert`对应合并提交；
- 错误任务状态：通过状态闭环PR按Git事实修正；
- 错误合并：普通`git revert`，不得改写历史；
- 数据、服务器和生产系统不在本流程范围，无此类回滚动作。

## 十、阶段2增强

正式开发阶段再评估GitHub Pro、Branch Protection、规则集、必需平台评审、CODEOWNERS、
原生Auto Merge、完整Quality Gate和组织级身份签名。这些能力不阻塞当前轻量闭环。

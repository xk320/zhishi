# 《知势》PR自动合并策略

> 当前阶段只自动化低风险PR在架构评审通过后的机械合并动作。自动化不能代替评审，
> 不能自行授予权限，也不能降低任务、研究、数据或风险门槛。

## 一、适用阶段与平台边界

本策略适用于阶段0.5研究与架构建设期间的GitHub Free私有仓库。

当前仓库没有私有仓库Branch Protection、规则集、必需评审和原生Auto Merge。
因此使用两个仓库内GitHub Actions工作流建立轻量替代流程：

- `pr-auto-merge-eligibility.yml`：只读检查PR是否属于可自动合并范围；
- `pr-auto-merge.yml`：接受架构批准，使用`main`上的可信规则复验并合并。

任务-000013是引导变更。其工作流尚未进入`main`，且PR本身修改`.github/`，必须
人工评审和合并。后续变更才可使用本策略。

## 二、职责分离

| 角色 | 可以做什么 | 不可以做什么 |
| --- | --- | --- |
| Codex | 执行任务、验证、创建PR、更新待评审记录 | 不得给出架构批准，不得伪造所有者指令 |
| 仓库所有者`xk320` | 评审当前PR头提交并发出绑定SHA的批准指令 | 不得用未绑定SHA的口头结论触发自动合并 |
| 资格检查工作流 | 读取PR内容并报告资格 | 没有写权限，不能合并 |
| 合并工作流 | 使用`main`可信脚本复验并合并精确SHA | 不执行PR分支代码，不扩大任务范围 |

自动合并的授权来自仓库所有者的架构批准，不来自Codex、PR作者、标签、Issue、
资格检查结果或任务状态本身。

## 三、标准流程

```text
任务文件进入main
    ↓
Codex独立分支执行、验证并创建PR
    ↓
只读资格工作流检查
    ↓
Codex将任务更新为待评审
    ↓
仓库所有者评审当前头提交SHA
    ↓
评论：/架构评审通过 <40位SHA>
    ↓
main可信工作流复验全部条件
    ├── 通过：合并精确SHA并写入审计评论
    └── 失败：停止，保留人工处理
    ↓
Codex按任务中心协议更新已完成证据
```

工作流失败时不自动重试、不使用管理员绕过、不降低门槛。评审者应先检查失败原因；
若PR提交发生变化，必须重新评审新SHA并重新发出批准。

## 四、批准指令

唯一有效格式：

```text
/架构评审通过 0123456789abcdef0123456789abcdef01234567
```

必须同时满足：

1. 评论位于目标Pull Request。
2. 评论由GitHub登录名`xk320`创建。
3. GitHub事件中的作者关联为`OWNER`。
4. 指令仅包含命令和40位小写十六进制SHA。
5. SHA等于评论发生时和合并前的PR头提交。

评论创建后若PR新增提交，旧批准失效。编辑旧评论不会触发合并，必须对新SHA创建
新的批准评论。

## 五、任务资格

任务类型必须从基线`main`中的任务文件读取，不能信任PR对自身类型的修改。

允许自动合并的类型只有：

- `类型：文档`
- `类型：治理`
- `类型：研究规范`

任务类型缺失、未知或属于其他类型时，PR仍可正常评审和人工合并，但不能自动合并。

每个自动合并PR还必须满足：

1. PR正文引用至少一个`任务-NNNNNN`。
2. 每个关联任务文件已在基线`main`存在。
3. PR中的关联任务状态为`待评审`。
4. PR实际修改的任务文件与正文引用一致。
5. 目标分支为`main`，来源仓库为`xk320/zhishi`。
6. PR为开放、非草稿、可合并状态。
7. 当前提交的资格检查已成功执行。

## 六、文件资格

当前阶段只允许以下Markdown路径自动合并：

- `AGENTS.md`
- `README.md`
- `《知势宣言》.md`
- `docs/`下的`.md`文件

以下路径和变更一律转人工：

- `.github/`及任何工作流；
- `scripts/`、`tests/`和源代码；
- 依赖、构建、部署和生产配置；
- 数据文件、数据库迁移、删除或覆盖操作；
- 交易执行、资金管理、账户权限和真实资金相关实现；
- 任何无法由规则明确分类的文件。

路径资格只是自动合并的必要条件，不代表内容已经通过架构评审。最终批准仍由仓库
所有者对具体SHA给出。

## 七、工作流安全

### 只读资格检查

- 由`pull_request`事件触发。
- 权限只有`contents: read`和`pull-requests: read`。
- 可以运行PR分支中的资格脚本，但没有写入或合并能力。
- 不符合自动合并资格时正常报告“转人工”，不把人工PR伪装成工程失败。

### 合并工作流

- 由`issue_comment.created`触发，工作流必须已存在于默认分支。
- Action依赖固定到完整提交SHA。
- 不使用`pull_request_target`。
- 评论正文通过环境变量传递，不直接拼接进Shell脚本。
- 先确认所有者、PR、来源仓库、目标分支、批准SHA和资格检查。
- 只检出`main`，只运行`main`上的可信资格脚本。
- 可以获取PR提交用于只读比较，但不执行其中代码。
- 合并API必须携带预期头提交SHA，防止检查与合并之间提交被替换。
- 令牌权限限定为读取检查、写入合并结果和审计评论所需的最小范围。

## 八、任务状态与证据

GitHub Actions当前不直接提交到`main`修改任务状态。合并后由Codex按任务中心协议
记录：

- 合并提交SHA；
- 完成时间；
- 验收与验证结果；
- 数据与安全影响；
- 任务文件与看板的`已完成`状态。

这样避免建立会直接写入`main`、自动创建循环PR或绕过任务文件唯一事实来源的第二套
状态系统。

## 九、失败、人工处理与回滚

出现以下任一情况时停止自动合并：

- 批准指令无效或SHA过期；
- PR草稿、关闭、冲突、落后或GitHub未确认可合并；
- 资格检查缺失、异常或失败；
- `main`可信规则复验不通过；
- GitHub API拒绝合并。

停止后保留PR和工作流日志，由人工决定修复、重新评审或普通合并。禁止为完成任务而
修改规则跳过失败条件。

回滚方式：

- 工作流异常：禁用或通过PR回滚工作流文件。
- 策略异常：回滚资格脚本和本策略文档。
- 错误合并：对合并提交执行普通`git revert`，不改写历史。

## 十、阶段2增强

正式开发阶段评估并实施：

- GitHub Pro或适合的组织级付费方案；
- `main` Branch Protection或规则集；
- 必需架构评审、CODEOWNERS和必需状态检查；
- 原生Auto Merge；
- 完整Quality Gate；
- 合并后任务状态的端到端自动同步。

以上能力不作为任务-000013验收条件，也不阻塞当前研究与架构任务。

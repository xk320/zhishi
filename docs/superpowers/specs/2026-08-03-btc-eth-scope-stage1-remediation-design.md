# BTC、ETH研究范围与阶段1数据闭环修复设计

## 一、目标

本设计落实三项连续目标：

1. 修复当前规范性文档中的阶段、服务器、任务和能力状态漂移；
2. 将《知势》前向正式研究范围从BTC、ETH、SOL收缩为BTC和ETH；
3. 按数据硬门依赖顺序完成来源身份、三类时间、质量、重放、成本、独立闭环、
   最小闭环试点、容量恢复和最终审计，直到形成新的阶段2放行或禁止证据。

任务完成不等于阶段通过。阶段2只能由新的不可变审计批次明确放行，不能因为移除SOL、
完成文档或完成任务数量而自动解锁。

## 二、已批准方案

采用“前向范围收缩、历史证据保留、阶段门重新验证”的单一路径。

- 现行规范、未来任务、研究、模型、回测、许可和复盘只覆盖BTC、ETH；
- 历史任务记录、已发布审计报告、批次清单和历史统计保持不可变，其中出现SOL时明确
  属于当时范围和历史证据，不代表现行范围；
- 总体计划负责阶段状态，任务文件负责任务状态，看板只派生任务状态；
- 新增自动检查，拒绝规范性文档继续出现旧服务器状态、旧任务状态或SOL前向范围；
- 阶段1缺口按硬门顺序拆成独立任务，后序任务不得补偿前序失败；
- 只在BTC和ETH各自全部通过阶段1六道门后评估阶段2，禁止跨标的补偿。

## 三、方案取舍

### 3.1 采用：前向收缩并保留历史

该方案不篡改既有审计事实，同时确保任何新能力只以BTC和ETH为范围。它符合不可变历史、
任务文件唯一事实来源和数据安全原则。

### 3.2 不采用：全仓机械删除SOL

机械删除会改写历史任务合同、审计分母、批次结论和已合并证据，使旧报告无法复现，并可能
把原先的SOL缺失错误地隐藏成“从未要求”。

### 3.3 不采用：把SOL保留为可选标的

可选范围会继续迫使数据、研究、接口和测试维护第三套作用域，并给跨标的补偿留下歧义，
不符合用户明确要求的BTC、ETH双标的范围。

## 五、阶段状态模型

现行阶段仍为0、0.5、1至7，共九个阶段。当前事实固定为：

- 阶段0：已完成；
- 阶段0.5：核心理论合同已完成；
- 阶段1：审计与合同任务已交付，但能力门未通过，处于修复中；
- 阶段2：被阶段1阻塞；
- 阶段3至7：允许保留理论合同，不得宣称运行能力已开始或已完成；
- 真实资金：关闭，不属于自动解锁阶段。

阶段状态变更必须引用阶段门审计版本、批次、指纹和结论。服务器可访问只解除连接条件，
不等于阶段1通过。

## 六、任务依赖链

任务-000028负责治理收口和登记后续任务；其余任务严格顺序执行：

```text
任务-000028 统一阶段状态与BTC/ETH范围
  → 任务-000029 来源与标的身份合同
  → 任务-000030 三类时间与数据对象质量合同
  → 任务-000031 输入身份修复与完整只读质量审计
  → 任务-000032 可信重放来源与决策现场记录
  → 任务-000033 成本、流动性与执行数据闭环
  → 任务-000034 BTC、ETH独立数据闭环
  → 任务-000035 最小数据闭环试点
  → 任务-000036 容量试采与隔离恢复演练
  → 任务-000037 最终复验与阶段2门禁裁决
```

每个任务只允许产生本任务范围内的新版本和聚合证据，不修改原始数据或历史批次。任一
阶段门失败或无法判定时，后序诊断可以保留证据，但不能形成阶段放行。

## 七、数据与安全设计

- 远端仅使用已批准的SSH逻辑别名`ubuntu`和显式白名单；
- 文件、SQLite和市场数据只读，数据库访问不得扩大既有授权；
- 不删除、覆盖、修复、重排、静默去重或补写原始数据；
- 新样本、标准化对象、快照和恢复副本只能写入隔离的新版本路径；
- 所有处理必须流式、有界内存、有界磁盘、有界输出和有界超时；
- 当前本机可用磁盘较低，试点必须预检空间并使用小型、可删除的隔离临时目录；
- 不训练模型、不运行策略回测、不生成胜率、收益、方向、仓位、订单或真实交易许可；
- 任何凭据、IP地址、原始市场正文和未脱敏样本不得进入Git。

## 八、错误处理

每个阶段门至少支持`通过`、`拒绝`、`无法判定`、`失败`、`未成熟`和`失效`。未知字段、
来源冲突、时间不可见、身份漂移、输出超限、磁盘不足或远端失败都必须安全停止并保留
原因，不得返回上一批通过结果。

BTC和ETH必须分别判定；一个标的通过不能补偿另一个标的失败。删除SOL只改变前向范围，
不能把BTC或ETH原有的来源、时间、质量、重放和成本缺口改写为通过。

## 九、验证策略

1. 任务与看板唯一映射、标准状态和合同字段检查；
2. 规范性文档前向范围检查，确保只包含BTC、ETH；
3. 历史证据保护检查，确保已发布审计批次指纹不变；
4. 阶段状态引用检查，拒绝“等待服务器”“任务尚未完成”等失效现状；
5. 每个数据任务采用测试先行，验证身份、时间、只读、资源限制、不可变发布和失败安全；
6. 最终复验重新生成独立批次，明确阶段2为`允许`或`禁止`，不接受模糊状态。

## 十、完成定义

完整目标只有在以下事实同时成立时完成：

- 所有现行规范和阶段状态一致，自动漂移检查通过；
- 前向研究范围只包含BTC、ETH，历史证据未被改写；
- 任务-000028至任务-000037均经过评审并合并；
- BTC、ETH分别形成来源、三类时间、质量、重放、成本、血缘、快照和恢复证据；
- 最终审计批次可复现，任务中心与看板状态一致；
- 阶段2门禁得到明确、真实、可验证的裁决；
- 未执行模型训练、策略回测或真实资金交易。

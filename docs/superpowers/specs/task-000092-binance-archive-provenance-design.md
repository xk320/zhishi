# 任务-000092 Binance 历史归档来源身份设计

<!-- markdownlint-disable MD013 -->

## 问题与边界

本地`/Volumes/data/data/binance/futures/um`已有约154GiB归档。BTC trades约65.75GiB，2932个ZIP与2932个CHECKSUM全配对；ETH trades约74.79GiB，2445对；BTC aggTrades约7.55GiB，423对。旧数据具备高价值，但当前没有逐文件内容哈希、官方对象身份、Schema和九字段来源记录，不能直接进入研究链路。

任务-000084的630个成员来自Ubuntu旧候选资产，与这些本地归档不是同一分母。本设计建立新的替代来源候选集，不改写旧成员或阶段门禁。

## 方案比较与固定决策

- 复用本地归档并全量验证：只增加小型证据批次，保留旧数据，能用CHECKSUM与官方对象清单形成逐成员证据。采用。
- 仅抽样验证：速度快，但不能证明未抽样成员，无法形成确定分母。不采用。
- 全量重新下载：需要额外约200至220GiB，仍需相同身份和完整性验证，成本高且没有必要。只允许后续对失败成员选择性补采。

用户已批准复用旧数据方案。执行实现不得再次提出方案选择。

## 身份证明链

```text
固定本地普通ZIP
    ↓ 同名严格配对
本地CHECKSUM（精确文件名 + SHA-256）
    ↓ 1MiB块流式复算
ZIP内容SHA-256全等
    ↓ 固定公开S3对象清单
官方ZIP键存在 + 字节数全等
    ↓ 官方CHECKSUM对象ETag
本地CHECKSUM字节MD5全等
    ↓ ZIP中央目录与有界表头
Schema确切版本指纹
    ↓ 九字段 + 内容SHA + 证据定位
新的Binance归档来源候选集
```

任何一环失败，只影响对应成员并进入结构化异常清单；不得回退到目录名、聊天说明或模糊匹配。

## 组件

1. 配置校验器：固定本地根、三组成员、两个观察项、远端桶/前缀、命名规则和资源上限。
2. 发现器：按UTF-8文件名字节序确定性枚举普通ZIP与CHECKSUM，拒绝越界、符号链接、隐藏资源分叉和未知文件。
3. 完整性验证器：严格解析CHECKSUM，以1MiB块复算ZIP SHA-256，不把ZIP内容写入输出。
4. 官方清单读取器：固定系统curl、可信TLS、串行S3分页；只保留对象键、Size、ETag和LastModified的规范化指纹。
5. Schema验证器：检查ZIP只有一个同名普通CSV成员，最多解压读取1MiB用于列数、表头形状和Schema指纹；不保存业务行。
6. 身份裁决器：对来源、场所、市场、标的、合约、对象、Schema、授权和字段映射逐项裁决，输出紧凑成员记录。
7. 批次发布器：按BTC/ETH和数据对象分片，以临时目录构建后原子改名；禁止覆盖历史批次。

## 数据与资源

执行只顺序读取本地约154GiB数据，不创建副本。单个文件最大16GiB，成员最大8192，哈希块1MiB，进程内存上限256MiB，批次总超时14400秒。公开清单累计最大32MiB，日志最大64KiB，仓库输出单文件小于5MiB、总计小于25MiB，本地新增磁盘预算不超过1GiB。

## 失败安全

固定根不可读、配对缺失、哈希不一致、官方键缺失、大小不一致、ETag不可用、ZIP异常、Schema不一致、超时、超限、计数不守恒或源目录漂移均产生稳定失败码。失败不得触发自动下载、删除、修复、重命名、解压落盘或阶段放行。

## 测试设计

- 用临时小ZIP和CHECKSUM先写失败测试，覆盖严格配对、哈希、路径、ZIP成员、Schema、官方对象匹配、ETag、确定性排序和原子发布。
- 使用伪造的小型公开清单响应测试分页、重复对象、未知前缀、超限和TLS/参数边界；单元测试不访问网络。
- 集成验证运行真实全量本地哈希与固定公开清单读取，记录执行前后源目录清单指纹和资源事实。
- 数据质量报告按数据集/标的呈现覆盖率、异常率、时间范围和选择性补采量，不把来源通过解释为内容质量或研究准入。

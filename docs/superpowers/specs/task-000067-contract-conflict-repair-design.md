# 任务-000067设计：任务完成定义冲突的受控合同修复

## 问题

任务-000066的正文只读质量复验交付PR #165已经进入`main`，但其登记阶段合同仍要求“本登记PR合并后任务保持阻塞”。
状态闭环PR #166因此被可信检查器正确拒绝。另一个事实冲突是任务文件记录“实现提交SHA”，而自定义主题合并事实复算要求“交付提交SHA”。
直接放宽状态闭环会使任务合同不再是唯一事实来源。

## 方案

新增一次性变更类型“任务合同冲突修复”，固定映射：

```text
执行任务：任务-000067
目标任务：任务-000066
目标基线状态：待评审
目标头部状态：待评审
允许字段：交付提交SHA、完成定义
```

可信资格器从main的任务文件和真实Git对象复算交付SHA，不能从PR正文、Issue或聊天读取。完成定义采用完整旧/新段落指纹，
不接受正则宽松替换。目标任务的看板行、状态、依赖、范围、输入输出、安全边界和审计结果必须逐字保持。

## 失败安全

以下任一情况失败关闭：错目标、多个目标、目标状态迁移、目标看板漂移、缺少交付SHA、SHA不是PR #165交付头、
SHA不在合并第二父链、完成定义部分替换、夹带第三字段、修改生产/数据路径、修改普通状态闭环规则或缺少双只读评审。

## 后续闭环

本设计合并后，任务-000066仍保持`待评审`。Codex必须从最新main创建独立状态闭环PR，重新绑定任务-000066真实合并事实，
通过双只读评审和可信复验后才可标记`已完成`。本设计不把“无法判定”“失败”或“未成熟”转换为通过，也不解除阶段1数据硬门。

## 验证

- Python标准库单元测试和固定Git夹具覆盖正向与越权反例。
- 研发中心全量测试、Python编译、MarkdownLint、敏感信息扫描和`git diff --check`必须通过。
- 全过程只读本地Git对象和仓库文件，不访问服务器、数据库、真实市场数据或生产系统。

# 任务-000067设计：任务合同冲突修复的可信引导路径

## 问题

任务-000066的正文只读质量复验交付PR #165已经进入`main`，但其登记阶段合同仍要求“本登记PR合并后任务保持阻塞”。
状态闭环PR #166因此被可信检查器正确拒绝。另一个事实冲突是任务文件记录“实现提交SHA”，而自定义主题合并事实复算要求“交付提交SHA”。
直接放宽状态闭环会使任务合同不再是唯一事实来源。

当前`main`的可信资格器只认识既有四种变更类型。若同一个普通任务交付PR首次引入新变更类型并修改任务-000066，
基线解析会拒绝新类型；若使用普通任务交付类型直接修改任务-000066，跨载体合同漂移检查会拒绝既有任务合同。因此必须分两步引导。

## 两步方案

### 第一步：任务-000067（本任务）

本任务使用基线已支持的`任务交付`变更类型，只修改可信治理脚本、工作流解析、治理策略和测试，建立并验证新类型，
但不修改任务-000066。新类型预绑定下一编号任务-000068→任务-000066，具体固定事实为：

```text
引导任务：任务-000067
未来执行任务：任务-000068
目标任务：任务-000066
目标基线状态：待评审
目标头部状态：待评审
允许字段：交付提交SHA、完成定义
```

任务-000067交付PR合并后，先以独立状态闭环PR标记任务-000067完成，再登记任务-000068。这样新变更类型已经存在于
`main`，不会出现同一PR的基线引导死锁。

### 第二步：任务-000068（后续任务）

任务-000068从包含本引导规则的最新`main`创建执行分支，使用新变更类型，只允许修改任务-000066的两项字段。可信资格器
从main中的“实现提交SHA”、PR #165真实双父合并提交和祖先关系复算“交付提交SHA”，不信任PR正文、Issue或聊天。
“完成定义”采用完整旧/新段落指纹，不接受正则宽松替换。任务-000066状态、看板行、依赖、范围、输入输出、安全边界、
审计批次、失败计数和研究结论必须逐字保持。任务-000068合并并闭环后，才能重新创建任务-000066的独立完成状态闭环PR。

## 失败安全

以下任一情况失败关闭：错目标、多个目标、目标状态迁移、目标看板漂移、缺少交付SHA、SHA不是PR #165交付头、SHA不在
合并第二父链、完成定义部分替换、夹带第三字段、修改生产/数据路径、修改普通状态闭环规则或缺少双只读评审。
任务-000067本身若修改任务-000066或在基线不支持的新类型上提交，必须失败关闭。

## 数据与阶段边界

本引导只修复仓库内可信治理路径，不访问服务器、数据库、真实市场数据或生产系统，不读取或修改原始数据，不生成胜率、
收益、模型、回测、方向、仓位、订单或交易许可。任务-000066的`无法判定`、`失败`和`未成熟`结果不因合同修复而变为通过，
阶段1数据硬门和阶段2禁止条件保持不变。

## 验证

- Python标准库单元测试和固定Git夹具覆盖两步引导、正向路径与越权反例。
- 研发中心全量测试、Python编译、MarkdownLint、敏感信息扫描和`git diff --check`必须通过。
- 第一步交付PR必须使用已有`任务交付`类型并通过基线可信资格器；第二步由任务-000068使用新类型并绑定精确头SHA。
- 全过程只读本地Git对象和仓库文件，不访问服务器、数据库、真实市场数据或生产系统。

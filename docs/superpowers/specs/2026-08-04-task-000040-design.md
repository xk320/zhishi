# 任务-000040设计：任务中心架构与看板校验器一致性治理

## 问题

任务中心看板的“待评审”表头曾使用`Pull Request`，而可信校验器合同使用`PR`。两处
重复定义造成任务-000029合并后状态闭环无法通过资格检查。仅修正当前一处文字不能防止
下一次任务登记、状态闭环或测试继续产生同类漂移。

## 设计原则

1. 看板模式只有一个机器合同来源，文档只解释语义，不重复定义可执行字段；合同覆盖七个标准状态分区；
2. 任务文件仍是任务状态和合同唯一事实来源，看板必须由任务文件可复算；
3. 任何未知表头、别名、重复列、缺列、错分区或任务行漂移都失败关闭；机器合同缺失、损坏或重复JSON键同样失败关闭；
4. 历史不可变交付物不改写，只规范当前可变治理入口；
5. 变更必须在可信`main`上验证，不能以PR自身代码替代基线校验器。

## 交付边界

- 机器合同：状态分区、表头、分隔行、任务行列顺序、版本和内容指纹；
- 可信校验器：统一加载并验证合同，输出稳定、可定位的失败原因；
- 控制面保护：机器合同路径只能由基线已授权的治理自动化任务修改；
- 任务交付：看板路径发生变更时，任务交付与任务登记、状态闭环一样复算看板模式和唯一映射；
- 测试：任务登记、任务交付、状态闭环以及当前任务映射的漂移回归；
- 文档：任务规范说明规范列名和冲突处理；
- 当前看板：将“Pull Request”规范化为“PR”。

## 不采用的做法

- 不保留多个同等权威的表头别名；
- 不用宽松正则或“看起来类似”规则放行；
- 不修改历史任务完成证据；
- 不把Issue、PR标题或聊天内容作为模式合同。

## 验收证据

- 机器合同内容指纹可复算；
- 当前看板和全部任务映射测试通过；
- 构造旧表头、重复表头、缺列和错分区样例均失败；
- PR #48在规范化基线后重新通过资格检查；
- 全量研发中心、审计、Markdown和差异验证通过。

# 阶段1数据缺失审计合同

<!-- markdownlint-disable MD013 -->

## 目的

本合同把任务-000084的后续工作收敛为“确认正式研究输入是否缺失、缺失在哪里、是否切断连续覆盖”。订单簿采集架构已经固定使用的Binance来源事实仅从已合并批次复用，不在本合同中重新证明来源提供者身份，也不创建`source-identity-evidence-1.0`清单。

任务-000084的旧合同、旧批次和失败证据保持不可变；任务-000109是替代执行入口。旧任务只有在任务-000109完成后，才可通过独立状态闭环记录取消，不得在本批次中伪造其完成。

## 固定输入

- 批次：`artifacts/审计/阶段1逐行时间质量/stage1-time-quality-20260812T091000Z-6968246516ef/`。
- 输入文件：`summary.json`、`members-001.json`、`segments.json`、`leaves.json`、`source-rejected.json`、`formal-batch-files.json`、`source-batch-files.json`。
- 输入必须与`config/审计/任务-000084数据缺失审计.json`中的SHA-256逐字节一致；漂移即失败安全。
- 研究标的独立统计：BTC、ETH；主研究尺度为4小时、8小时、24小时、48小时；15分钟和1小时只登记为事后结果观察窗口。

## 统计口径

每个数据对象按`标的、合约、数据集`精确分组，保留候选总体、正式成员、已观察、拒绝、无法判定、失败、未成熟、失效。`已证明`是当前批次中可用于连续覆盖的状态；拒绝日期和缺失日期均计入缺失覆盖。来源拒绝候选必须按原始`group`映射到BTC/ETH对象分母和八个尺度叶子，不能补入另一标的；正式成员状态和来源拒绝状态分别保存并同时给出合计状态，避免分母歧义。

连续段必须满足：起止日期按自然日解析，段内无空日，所有段互不重叠，段内已证明日期并集与`segments.json`完全相等。任何计数不守恒、成员重复、状态未知或分组漂移都停止发布。

## 输出与版本

执行器只用Python标准库，单进程、固定输入、无网络、无远端、无数据库访问。每次运行新建不可覆盖的`artifacts/审计/阶段1数据缺失/<批次>/`，保存：

- `summary.json`：候选总体、正式成员、来源拒绝、状态和缺失计数；
- `groups.json`：各标的、数据对象和连续覆盖段统计；
- `leaves.json`：BTC/ETH×4/8/24/48小时八个叶子裁决，含来源拒绝分组、连续段数量、覆盖日期数量和对象级覆盖明细；
- `missing-dates.json`、`missing-members.json`：缺失位置和成员；
- `rules.json`、`executor.json`、`manifest.json`：规则、执行器、输入/输出指纹和资源事实。

批次为追加式、内容寻址且不可覆盖。输出不包含价格、成交、订单簿正文、凭据或原始业务记录。

## 禁止推断

本合同不能推出来源身份新结论、因果关系、预测优势、胜率、收益、研究准入、交易许可、方向、仓位或订单。不能在结果可见后更换状态分类、筛选事件、修改分组、缩小分母或寻找最佳窗口；不能跨BTC、ETH补偿缺失。

## 验收与回滚

验收要求输入/规则/执行器/输出指纹可复算，状态与缺失计数守恒，历史任务-000084批次字节不变，专项与审计测试、研发中心测试、编译、MarkdownLint及`git diff --check`有真实记录。回滚仅删除本任务新增的合同、配置、执行器、测试、缺失批次和派生文档；不得删除、覆盖或迁移旧批次和原始数据。
